Methodology, Controls & Data Provenance — Auditor / Regulator Reference

This section documents, at an audit-defensible level, how Fortifai Kuber derives every rupee of flagged opportunity: the deterministic rules behind each of the four commercial levers, the Tier-2 AI pattern-analysis engine, the false-positive and exclusion criteria applied before anything reaches a user, and the governance workflow that dispositions each case. Kuber is read-only over a SAP replica; it surfaces signals for human review and posts nothing to the system of record. All figures on this prototype derive from a synthetic dataset and are illustrative.

1 · Three-Stage Processing Architecture

Every signal passes through three stages before a user sees it. This is what separates Kuber from a BI dashboard (which shows raw variance) and from an unconstrained LLM (which hallucinates over SAP tables).

StageFunctionInputs & controls
Stage 1
Ingest		SAP P2P replica + external spine25 SAP tables (EKKO, EKPO, EKBE, RBKP, RSEG, MSEG, BSIK, CDPOS, LFA1) joined on full composite keys (MANDT+BUKRS+GJAHR+BELNR); external commodity indices (LME / ICIS / CMA); D7 supplier-substance (EPFO workforce, GST HSN). Read-only (SELECT).
Stage 2
Condition		Commercial normalisation + noise suppressionTerms-Adjusted Price Bridge (UoM + ZTERM + Incoterms) so prices are compared like-for-like; then the 9 noise suppressants (see §7) strip intercompany, regulated-monopoly, ERS and genuine-emergency traffic.
Stage 3
Triage		Closed-loop human dispositionEach surviving signal is promoted to the Actions Hub (owner + SLA + note, minting a KBR-#### record) or suppressed as a false positive to the Exception Memory Register, with structural-drift tripwires. Full audit lineage retained.
Deterministic-first principle. All monetary math — UoM scaling, credit-carry, freight normalisation, arbitrage, recovery sizing — is computed by deterministic SQL and non-parametric statistics. Generative AI is used only to narrate evidence and draft the renegotiation brief; it never originates a number.
LEVER 1Price Optimisation & PO-to-Invoice Leakage

Detects where paid prices exceed a defensible benchmark after normalising for the three excuses category managers raise — packaging unit, credit terms, and freight. The normalisation bridge is the evidentiary core:

Base UoM Price (P_base) = (EKPO.NETPR / EKPO.PEINH) × (EKPO.BPUMN / EKPO.BPUMZ) Credit Carry Adj (Δ_cred) = P_base × r_WACC(10%) × ((Days(ZTERM_vendor) − Days(ZTERM_benchmark)) / 365) Effective Price (P^eff) = P_base − Δ_cred − Δ_Incoterm_Freight(INCO1)

6 · Tier-2 AI Pattern Analysis

Where Levers 1–4 test explicit rule breaches, the Tier-2 engine detects deviation from each subject's own learned baseline using non-parametric statistics — surfacing schemes that stay within every system tolerance. Tier-2 leads are indicative, carry a confidence score, are gated when the baseline is thin, and are de-duplicated against Lever 1–4 hits so the same transaction is never double-counted.

Median Absolute Deviation (MAD) = median( | x_i − median(X) | ) Modified Robust Z-Score (Z_rob) = 0.6745 × ( x_i − median(X) ) / MAD [lead triggers at | Z_rob | > 3.0σ]
PatternWhat it surfacesMethod
PAT-01Sub-tolerance creep clusterA vendor whose invoices cluster just under tolerance at a high robust-Z vs peer median
PAT-02Vendor spend surgeMonthly spend far above the vendor's own median (robust-Z on MAD)
PAT-03Out-of-trend PO valueA single PO far outside the vendor's own value distribution
PAT-04Share-of-business concentrationA vendor's share of a category rising structurally vs its baseline
PAT-05Thin-history concentrationSpend concentrating on a recently-onboarded vendor (gated — thin baseline)
PAT-06Related-party linkageNominally independent vendors resolving to a shared bank account / address (graph linkage)
Validation. The pattern engine is validated against a ground-truth evaluation set (synthetic records carrying a known answer key), so precision and recall are measured rather than asserted. These are evaluation-set figures evidencing the method is tested — not a production-accuracy claim.
7 · False-Positive & Exclusion Criteria

Transformation leaders reject tools that spam business users. Before any signal reaches a queue, Kuber applies 9 automated noise suppressants that remove legitimate traffic which would otherwise look anomalous. These are applied at Stage 2 and are fully logged.

Analyst false-positive suppression. Any surviving signal a reviewer judges benign — an authorised OEM distributor behind a CON-03 flag, an approved index spike, a verified emergency — is marked Mark FP and written to the Exception Memory Register, removing it from the active queue. A structural-drift tripwire re-surfaces it only if the underlying pattern changes materially (e.g. the suppressed vendor's markup widens beyond its historical band), preventing permanent blind spots.
Explicit exclusion boundaries. Kuber's scope is procurement cost and margin. It does not assert bribery, corruption or intent; it does not characterise any individual; and it does not treat a public-register signal (EPFO/GST) as proof. Items dependent on data not present in standard replicated P2P — employee–vendor identity matching (needs HR infotypes) and bid-metadata collusion (needs sourcing-system documents) — are out of scope for this build and are not represented as live.

  • Promotion to Actions Hub (+ Action Hub): assigns an owner, target date and execution note, minting a tracked KBR-#### record with an immutable detected-timestamp.
  • False-positive suppression (Mark FP): routes to the Exception Memory Register with a mandatory reason; structural-drift tripwires govern re-surfacing (see §7).
  • SLA aging vs turnaround (TAT): open items track live age since detection against severity SLAs — Critical 3d · High 7d · Medium 14d · Low 30d. On completion, age stops and closed TAT is permanently locked for audit.

  • Read-only guarantee: all access is SELECT-only against the SAP replica, AST-validated (sqlglot); there is no write path to the system of record.
